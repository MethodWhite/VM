## 1. Overview

SolidScript is not a standalone compiler. It is a **Vex metaprogramming library** that uses the existing Vex toolchain — VPP preprocessor, `@Macro` system, type checker, and SSA IR — to provide a graphics DSL. The entire transformation happens **at compile time** during Vex macro expansion.

### Architecture layers

```
                    ┌──────────────────────────────┐
                    │      SolidScript source       │
                    │         (.solid file)         │
                    └──────────────┬───────────────┘
                                   │
                                   ▼
                    ┌──────────────────────────────┐
                    │      @Solid annotation        │
                    │  (Vex @Macro, triggers DSL)   │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │  VPP Preprocessor             │
                    │  ┌─────────────────────────┐  │
                    │  │ #import <solid/std>      │  │
                    │  │ #define float3 ...       │  │
                    │  │ @vertex → @Macro gen     │  │
                    │  └─────────────────────────┘  │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │      Pure Vex AST             │
                    │  (all DSL lowered away)       │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │   Standard Vex pipeline        │
                    │   Type Check → SSA IR → .velb │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │   VestaVM Runtime              │
                    │   ┌─────────────────────────┐  │
                    │   │ Graphics FFI Layer       │  │
                    │   │ (Vulkan/Metal/DX12)      │  │
                    │   └─────────────────────────┘  │
                    └──────────────────────────────┘
```

## 2. Type Mapping

Every SolidScript graphics type maps to either a **Vex struct**, a **Vex `@opaque` handle**, or a **compile-time macro**.

### 2.1 Value types (Vex structs)

```vex
// ====== SolidScript → Vex struct mapping ======

// float2 → SolidFloat2
struct SolidFloat2 { x: f32, y: f32 }

// float3 → SolidFloat3
struct SolidFloat3 { x: f32, y: f32, z: f32 }

// float4 → SolidFloat4
struct SolidFloat4 { x: f32, y: f32, z: f32, w: f32 }

// color → SolidColor (alias for SolidFloat4 with swizzle overloads)
typedef SolidFloat4 SolidColor;

// matrix4x4 → SolidMatrix4x4
struct SolidMatrix4x4 { cols: [SolidFloat4; 4] }
```

Swizzle accessors (`v.xy`, `v.xyz`, `v.rgba`, etc.) are implemented as **Vex `@Macro` expressions** that detect the field access pattern at compile time and emit the correct struct field accesses. For example, `v.xyz` expands to:

```vex
SolidFloat3 { x: v.x, y: v.y, z: v.z }
```

### 2.2 Opaque handles (Vex `@opaque` structs)

GPU resources that cannot be represented as plain data use Vex's `@opaque` annotation, which tells the type checker that the struct is a fixed-size handle passed to FFI:

```vex
@opaque
struct SolidTexture {
    handle: u64,        // GPU descriptor handle
    width:  u32,
    height: u32,
    depth:  u32,
}

@opaque
struct SolidSampler { handle: u64 }

@opaque
struct SolidBuffer { handle: u64, size: u64, usage: u32 }

@opaque
struct SolidPipeline { handle: u64 }
```

These structs are passed by value to FFI functions. VestaVM's FFI layer knows how to convert them to the corresponding graphics API types.

### 2.3 Shader type (compile-time)

The `shader` type in SolidScript is **not a runtime type**. It is a compile-time concept implemented as a `@Macro` that generates:

1. A Vex struct `SolidShaderDescriptor` containing entry point names
2. Pipeline creation code that calls the graphics API via FFI
3. The SPIR-V/MSL/HLSI compilation step (delegated to the GPU driver at runtime)

```vex
// Generated by the @Solid macro for each shader definition
struct SolidShaderDescriptor {
    vertex_name:   string,
    fragment_name: string,
    compute_name:  string,      // empty if not a compute shader
    vertex_inputs: [SolidVertexInput; ..],
    uniforms:      [SolidUniformDesc; ..],
}
```

### 2.4 Material type (runtime struct)

```vex
struct SolidMaterial {
    pipeline:            SolidPipeline,    // compiled shader pipeline
    descriptor_sets:     [u64; 4],         // GPU descriptor set handles
    textures:            [SolidTextureBinding; ..],
    buffers:             [SolidBufferBinding; ..],
    blend_state:         SolidBlendState,
    depth_state:         SolidDepthState,
    raster_state:        SolidRasterState,
}
```

## 3. Shader Compilation Model

SolidScript shaders follow a three-phase model:

### Phase 1: Compile-time (Vex `@Macro` expansion)

1. `@vertex`, `@fragment`, `@compute` annotations are recognized by the `@Solid` macro
2. Each annotated function's AST is captured as a `comptime string` via Vex's `expr` capture
3. The `@Solid` macro generates:
   - A `SolidShaderDescriptor` with the function name as entry point
   - Metadata for vertex input layout, uniform bindings, push constants
   - Pipeline state creation code (blend, depth, raster)

### Phase 2: Runtime — Pipeline creation (VestaVM FFI)

When `solid_shader_create()` is called at runtime, VestaVM:

1. Receives the `SolidShaderDescriptor` from the macro-generated code
2. Passes the captured shader source/SPIR-V to the graphics API via FFI
3. Compiles shader stages (e.g., `vkCreateShaderModule`)
4. Links the pipeline (`vkCreateGraphicsPipelines`)
5. Returns a `SolidPipeline` opaque handle

### Phase 3: Draw time

```vex
// Generated by @Solid macro for each draw call
solid_draw(mesh, material);

// Lowers to:
//   vkCmdBindPipeline(material.pipeline)
//   vkCmdBindDescriptorSets(material.descriptor_sets)
//   vkCmdBindVertexBuffers(mesh.vertex_buffer)
//   vkCmdBindIndexBuffer(mesh.index_buffer)
//   vkCmdDrawIndexed(mesh.index_count)
```

## 4. The `@Solid` Macro Internals

The `@Solid` macro is the heart of SolidScript. It is implemented as a **Vex `@Macro`** that operates on the AST level.

```vex
@Macro
comptime string solid_transform(string source) {
    // 1. Parse the source for DSL patterns
    // 2. Transform vertex/fragment/compute blocks
    // 3. Generate pipeline descriptors
    // 4. Inject FFI bindings
    // 5. Return pure Vex code

    string result = source;

    // Phase A: Import standard library (if not present)
    if (!has_import(source, "solid/std")) {
        result = "#import <solid/std>\n" + result;
    }

    // Phase B: Transform type aliases
    //   float3 → SolidFloat3 (if not already a struct def)
    result = transform_types(result);

    // Phase C: Capture @vertex functions
    //   Wrap in @Macro that emits entry point info
    result = transform_vertex_functions(result);

    // Phase D: Capture @fragment functions
    result = transform_fragment_functions(result);

    // Phase E: Capture @compute functions
    result = transform_compute_functions(result);

    // Phase F: Generate pipeline descriptor initialization
    //   Creates SolidShaderDescriptor from captured metadata
    result = generate_pipeline_descriptor(result);

    // Phase G: Generate FFI stubs
    //   solid_draw, solid_begin_frame, etc.
    result = generate_ffi_stubs(result);

    return result;
}
```

### 4.1 Vertex shader transformation

A SolidScript vertex shader:

```solid
@vertex
VSOutput vs_main(VertexInput input) {
    out.position = modelViewProj * float4(input.position, 1.0);
    out.normal   = input.normal;
    return out;
}
```

Is transformed by `@Solid` into:

```vex
// Generated code
@Macro
comptime string vs_main_entry() {
    return `
        struct SolidVSEntry_vs_main {
            vertex_name:  "vs_main",
            input_layout: {
                { binding: 0, format: Float3, semantic: "POSITION" },
                { binding: 1, format: Float3, semantic: "NORMAL" },
            },
            output_slots: {
                { semantic: "SV_Position", format: Float4 },
                { semantic: "NORMAL", format: Float3 },
            },
        }
    `;
}

// Original function is kept as-is for type checking
@vertex
VSOutput vs_main(VertexInput input) {
    out.position = modelViewProj * float4(input.position, 1.0);
    out.normal   = input.normal;
    return out;
}
```

### 4.2 Uniform binding transformation

```solid
@binding(slot: 0, stage: Vertex)
uniform matrix4x4 modelViewProj;
```

Transforms to:

```vex
// Uniform is declared as an extern variable
// The @Solid macro generates the binding metadata
@Module(solid.generated)
extern matrix4x4 modelViewProj;
// Metadata is stored in a compile-time descriptor table
```

At runtime, `solid_material_set_uniform(mat, 0, mvp)` writes the value to the correct GPU descriptor slot via FFI.

## 5. Pipeline Lowering

The full pipeline lowering chain from SolidScript to GPU execution:

### 5.1 SolidScript source

```solid
shader my_pipeline = shader {
    vertex:   vs_main,
    fragment: fs_main,
    attributes: {
        { binding: 0, format: Float3, name: "position" },
        { binding: 1, format: Float3, name: "normal" },
    },
    uniforms: {
        { binding: 0, stage: Vertex, type: matrix4x4, name: "mvp" },
    },
};
```

### 5.2 Intermediate representation (post `@Solid`)

```vex
SolidShaderDescriptor my_pipeline_desc = SolidShaderDescriptor {
    vertex_name:   "vs_main",
    fragment_name: "fs_main",
    compute_name:  "",
    vertex_inputs: {
        SolidVertexInput { binding: 0, format: Float3, offset: 0, stride: 12 },
        SolidVertexInput { binding: 1, format: Float3, offset: 0, stride: 12 },
    },
    uniforms: {
        SolidUniformDesc {
            binding:   0,
            stage:     Vertex,
            type:      UniformMatrix4x4,
            name:      "mvp",
            size:      64,
        },
    },
};
```

### 5.3 FFI call to graphics API

```vex
// Generated pipeline creation
SolidPipeline my_pipeline = solid_pipeline_create(my_pipeline_desc);
// ↓
// VestaVM FFI → vkCreateShaderModule(VK_SHADER_STAGE_VERTEX_BIT, vs_main_spirv)
//             → vkCreateShaderModule(VK_SHADER_STAGE_FRAGMENT_BIT, fs_main_spirv)
//             → vkCreateGraphicsPipelines(...)
//             → returns VkPipeline handle wrapped in SolidPipeline
```

### 5.4 Draw call lowering

```vex
// SolidScript:
draw(mesh, mat);

// Lowered Vex:
solid_draw(mesh, mat);
// ↓
// VestaVM FFI → vkCmdBindPipeline(cmd, mat.pipeline)
//             → vkCmdBindDescriptorSets(...)
//             → vkCmdBindVertexBuffers(cmd, 0, mesh.vertex_buffer)
//             → vkCmdBindIndexBuffer(cmd, mesh.index_buffer)
//             → vkCmdDrawIndexed(cmd, mesh.index_count, 1, 0, 0, 0)
```

## 6. Material System

Materials are runtime objects managed by VestaVM's GC. The `@Solid` macro generates creation functions that:

1. Allocate a `SolidMaterial` struct on the GC heap
2. Create the GPU pipeline via FFI
3. Create descriptor sets for texture/uniform bindings
4. Return a `shared<SolidMaterial>` smart pointer

### Material instantiation

```vex
// SolidScript:
material mat = material::create { shader: pbr, textures: { ... } };

// Lowered Vex:
shared<SolidMaterial> mat = solid_material_create(
    pbr_pipeline,
    textures_array,
    uniforms_array,
    blend_state,
    depth_state,
    raster_state
);
```

### Material cloning

```vex
shared<SolidMaterial> mat2 = solid_material_clone(mat);
solid_material_set_texture(mat2, 0, new_tex);
// → creates new descriptor sets (immutable pipeline is shared)
```

## 8. SolidScript Compiler Architecture

The SolidScript "compiler" is actually a **Vex compile-time library** with these components:

### 8.1 File layout

```
solidscript/
├── std/                        # SolidScript standard library (Vex source)
│   ├── std.vex                 #  Core types, aliases, constants
│   ├── math.vex                #  Vector math, swizzle macros, matrix ops
│   ├── pipeline.vex            #  Pipeline descriptor generation
│   ├── material.vex            #  Material creation and management
│   ├── mesh.vex                #  Mesh creation and loading
│   ├── light.vex               #  Light types
│   ├── camera.vex              #  Camera helpers
│   ├── scene.vex               #  Scene graph
│   ├── noise.vex               #  Perlin/Simplex/Worley noise
│   └── postprocess.vex         #  Post-processing effects
├── solid.vph                   #  Entry point: #import chain
├── solid_macro.vex             #  @Solid macro implementation
├── solid_types.vex             #  Type lowering macros
├── solid_ffi.vex               #  FFI binding declarations
├── solid_transform.vex         #  AST transformation logic
└── backends/
    ├── vulkan.vex              #  Vulkan-specific lowering
    ├── metal.vex               #  Metal-specific lowering
    └── dx12.vex                #  DirectX 12-specific lowering
```

### 8.2 Compile-time execution flow

```
VPP encounters @Solid
    │
    ▼
VPP processes #imports: <solid/std>, <solid/math>, etc.
    │
    ▼
solid_macro.vex @Macro fires
    │
    ▼
Macro captures body text as comptime string
    │
    ▼
Phase A: Import detection (add std if missing)
    │
    ▼
Phase B: Type transformation (float3 → SolidFloat3 via regex/replace)
    │
    ▼
Phase C: @vertex detection
    │   For each @vertex fn:
    │   1. Capture function AST via expr capture
    │   2. Generate entry point descriptor
    │   3. Generate vertex input layout
    │
    ▼
Phase D: @fragment detection (same pattern)
    │
    ▼
Phase E: @compute detection (same pattern + local size handling)
    │
    ▼
Phase F: Pipeline descriptor generation
    │   Collect all @vertex/@fragment/@compute entries
    │   Generate SolidShaderDescriptor struct literal
    │
    ▼
Phase G: FFI stub injection
    │
    ▼
Return pure Vex code → standard Vex pipeline continues
```

### 8.3 Swizzle macro implementation

```vex
// Swizzle accessors are predefined macros
// solid/std/vector_swizzle.vex

@Macro
comptime string swizzle_xy(string expr) {
    // Given expression "v", emit SolidFloat2 { v.x, v.y }
    return `SolidFloat2 { x: ${expr}.x, y: ${expr}.y }`;
}

@Macro
comptime string swizzle_xyz(string expr) {
    return `SolidFloat3 { x: ${expr}.x, y: ${expr}.y, z: ${expr}.z }`;
}

@Macro
comptime string swizzle_xyzw(string expr) {
    return `SolidFloat4 { x: ${expr}.x, y: ${expr}.y, z: ${expr}.z, w: ${expr}.w }`;
}

// Swizzle combinations: xy, xz, yz, xyz, xyw, yzw, xyzw, ...
// And color: r, g, b, a, rg, rb, gb, rgb, rgba, ...
// And texture: s, t, p, q, st, sp, tp, stp, stpq, ...
```

For performance, common swizzles are single struct field accesses (e.g., `.xyz` = the whole struct), while complex rearrangements (`.wyzx`) generate temporary struct literals.

### 8.4 Operator overloading via macros

Vex does not support operator overloading natively, so SolidScript uses macros to implement vector math operators:

```vex
// float3 + float3
@Macro
comptime string add_float3(string a, string b) {
    return `SolidFloat3 {
        x: ${a}.x + ${b}.x,
        y: ${a}.y + ${b}.y,
        z: ${a}.z + ${b}.z,
    }`;
}

// float3 * f32 (scalar multiplication)
@Macro
comptime string mul_float3_scalar(string v, string s) {
    return `SolidFloat3 {
        x: ${v}.x * ${s},
        y: ${v}.y * ${s},
        z: ${v}.z * ${s},
    }`;
}
```

These are invoked implicitly by the `@Solid` macro when it detects arithmetic between vector types.

## 9. Memory Model

### 9.1 CPU-side

- `SolidMesh`, `SolidMaterial`, `SolidTexture` → VestaVM GC heap (`shared<T>`)
- `SolidFloat2/3/4`, `SolidMatrix4x4` → stack-allocated value types
- `SolidShaderDescriptor` → compile-time constant (fossilized in `.velb`)

### 9.2 GPU-side

- Vertex/index buffers → allocated in GPU memory (mapped via FFI)
- Textures → allocated in GPU memory (upload via staging buffer)
- Descriptor sets → allocated per-material, updated via `vkUpdateDescriptorSets`
- Push constants → fast-access GPU memory (updated per-draw)

### 9.3 Data flow

```
CPU (VestaVM)                          GPU
─────────────                          ───
SolidMesh (GC)                         Vertex Buffer (VRAM)
    │                                        ▲
    └── solid_buffer_create_gpu() ──────────┘
                                         
SolidTexture (GC)                        Texture (VRAM)
    │                                        ▲
    └── texture::load() → FFI decode ────────┘
                                         
SolidMaterial (GC)                       Descriptor Sets
    │                                        ▲
    └── solid_material_create() ─────────────┘
                                         
SolidPipeline (GC)                       VkPipeline
    │                                        ▲
    └── solid_pipeline_create() ─────────────┘
```

## 10. Extending SolidScript

### 10.1 Adding a new type

```vex
// In solid_types.vex:
struct SolidDouble3 { x: f64, y: f64, z: f64 }

// Add type alias to solid/std:
typedef SolidDouble3 double3;

// Add math ops to solid/math:
@Macro comptime string add_double3(string a, string b) { ... }
```

### 10.2 Adding a new built-in function

```vex
// In solid/std/math_ext.vex:
@Macro
comptime string fresnel_schlick(string HdotV, string F0) {
    return `(${F0} + (1.0 - ${F0}) * pow(1.0 - ${HdotV}, 5.0))`;
}
```

### 10.3 Adding a new backend

```vex
// Create backends/custom.vex
// Implement the FFI call interface:

@Macro
comptime string backend_create_pipeline(string desc) {
    // Generate custom graphics API calls
}

// Select via:
//   #define SOLID_BACKEND_CUSTOM
//   #import <solid/backends/custom>
```

### 10.4 Custom shader stage

```solid
// Define new stage annotation
@Macro
comptime string tessellation_entry(string body) {
    // Capture tessellation control/evaluation shader
    // Generate hull/domain shader SPIR-V
}

// Usage:
@tessellation(max_tess_level: 16)
void ts_main(...) { ... }
```

## A. Performance Considerations

| Operation | Cost | Location |
| :-------- | :--- | :------- |
| Type lowering (`float3` etc.) | Zero (compile-time) | VPP macro phase |
| Swizzle access | 0-1 struct literal | Compile-time expansion |
| Shader compilation | GPU driver time | Pipeline creation |
| Draw call dispatch | ~0.1-0.5µs | Each `solid_draw()` |
| Material creation | ~50-200µs | Material setup |
| Texture load | Variable (disk I/O) | Asset loading |

## B. Dependencies

- **Vex compiler** (VestaVM toolchain) — provides lexer, parser, type checker, SSA IR
- **VPP preprocessor** — `@Macro` expansion, `#import`, `#define`
- **VestaVM runtime** — GC, FFI, threading
- **`libvesta_gfx`** — graphics abstraction layer (Vulkan/Metal/DX12)
- **Shader compiler** — glslangValidator / DirectXShaderCompiler / Metal shader compiler (invoked via FFI at runtime)

## C. File Format

SolidScript uses the standard Vex `.velb` bytecode format. No custom binary format is needed — all graphics metadata is stored as Vex data structures within the `.velb` sections, and pipeline creation happens at runtime via FFI.
